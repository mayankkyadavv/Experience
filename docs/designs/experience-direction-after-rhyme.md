## Problem Statement

The founder found that Rhyme (formerly Roamy, rhyme.travel) already does much of the original concept well: it imports Instagram/TikTok saves, extracts places, puts them on a map, builds itineraries, supports group trips, and suggests spots. The current docs frame Experience close to "share a travel reel → pin → trip", which Rhyme already owns. The docs need to (1) record Rhyme honestly, (2) restate the thesis as "Experience learns what you want to do from the content that inspires you, then helps you actually do it", and (3) separate long-term vision from current requirements so agents don't build Rhyme's feature list.

## Demand Evidence

- **Category demand is real.** At least 8 shipping apps do share-reel-to-map (Rhyme, Travio, Triply, GeoTok, Korka, glide, Go There, others). Rhyme has an App Store listing with a paywall. A design teardown reports it extracted 14 places from one Rome reel ([screensdesign](https://screensdesign.com/apps/roamy-save-spot-plan-trips/)).
- **No evidence yet of an advantage over Rhyme.** The founder ran their own saved reels through Rhyme end to end: "Yes, and it mostly worked." No specific failure was observed. Every proposed difference (activity over place, local use, preference learning, drive-to-done) is a hypothesis.
- **Still unproven from the prior session:** that resurfacing makes people actually go. No app in the category publishes visit or done rates.

## Status Quo

- Travel saves: Rhyme works for the founder today.
- Everyday saves: the native Save/bookmark button, which costs one tap and is never revisited (unchanged from the prior design).

## Target User & Narrowest Wedge

- The founder's friend group via TestFlight (ledger D5, unchanged).
- **The wedge is picked by data, not declared.** The app accepts every save. Each save records its category and whether it is local (near the user's home area) or travel. Nothing travel-only (itineraries, trip dates) is built in the MVP. If friends' saves and dones cluster in travel, travel becomes the wedge. If they cluster local, local does.

## Constraints

- All non-negotiables in CLAUDE.md stand: no video download or re-hosting, provenance on every field, Instagram URL-only, the cache terms, the outbox, the notification cap.
- **New consequence:** the "never download video" rule limits the brief's multimodal eval ladder. Transcript and full-video vision need video/audio access. Allowed signals today: captions/titles via official endpoints, oEmbed thumbnails (pending the terms check), web search, the user's hint.

## Premises (agreed)

1. Differentiation from Rhyme is unproven. Docs say "hypothesis" wherever they imply an advantage. Finding one real gap is the top research task.
2. The root domain object is an **Experience**: an activity plus intent, linked to zero or more Places, with a location requirement (`exact` / `flexible` / `none`). Place is a separate entity. This extends the ledger's model (which already has location-less "ideas").
3. The MVP stays narrow: no itineraries, groups, friends, onboarding quizzes or recommendations. The one MVP change: extraction also returns the activity/intent behind a save, alongside place candidates.
4. The Eng Review ledger stays in force. The new docs reorganize and extend it and don't reopen settled decisions. The one explicit amendment is ADR-006 (the Experience object's shape, and R1's key moving to `sources`), which follows from premise 2.
5. When the company outcome and the engineering outcome conflict, the company outcome wins.

## Approaches Considered

- **A: Patch in place.** Rejected: it leaves vision and requirements mixed in the same files, the confusion the brief's section 18 warns about.
- **B: Restructure into the brief's layout.** Chosen.

**Domain model (ADR-006), MVP shape.** ADR-006 **amends** the Phase 1 Experience object (inline `location {…}` and `source {…}` become separate tables). Everything else in the ledger is unchanged.

Every user-data table carries `user_id`, with the RLS policy "owner can read and write own rows". This keeps policies one-line and avoids joins in RLS.
- `sources` (one row per shared post): `id, user_id, save_id, url, platform, creator, user_hint (Sourced, provenance user), saved_at`. **R1 re-specified:** unique index `(user_id, save_id)` lives here. A replayed upload returns the existing source row. Identification runs once per source (the `jobs` row is keyed by `source_id`). A retry replaces that source's candidates and never creates a second set of Experiences. Test: replaying the same outbox item twice yields one source and one set of Experiences.
- `experiences`: `id, user_id, source_id, title (Sourced), intent (Sourced), category (Sourced), location_requirement (Sourced: exact|flexible|none), status, confidence, user_confirmed, timestamps`. `source_id` replaces `source_group_id`. Every AI-inferred field is `Sourced`: `estimated` by default, `source` when read literally from the post (e.g. a venue name in the caption), `user` when corrected. It's rendered only through `SourcedText` (ledger R8).
- `experience_places`: `user_id, experience_id, place_ref, role (primary|candidate), confidence`. Chain branches are not stored. They're resolved at runtime per R5.
- `places`: a **shared provider cache**, not user data. Keyed by `(provider, place_id)`, holding only `lookup`-provenance fields with per-field expiry (ledger storage rule). Clients have read-only access. It's written only by the `identify` function (service role). User-typed hints never go here; they live on `sources.user_hint` and the user's own Experience.
- `identification_candidates`: `user_id, source_id, candidates (jsonb: each interpretation with its evidence, confidence, model), created_at`. Kept with its source. Deleted with the account (ledger R7d). Retention 12 months, same as logs.

**One post → how many Experiences (the extraction rule):**
- Things the user would do separately become **separate Experiences** ("top 5 bars in Philly" → 5). They share `source_id`, so the UI's "5 places from this reel" is a count by `source_id` (same as the ledger's grouping). Did it is per Experience.
- Alternative places for doing **the same thing** become **one Experience with several candidate places** (an igloo-under-the-Northern-Lights reel → one Experience, "Dinner in a glass igloo under the Northern Lights", with the shown hotel as primary and any others as candidates).

**Behavior per `location_requirement` (MVP):**

| | exact | flexible | none (= the ledger's "idea") |
|---|---|---|---|
| Example | Joe's Pizza on Carmine St | Drive a race car on a real circuit (shown at Spa) | A recipe, "go stargazing" |
| Feed card / mini-map | Pans to the primary place (ledger) | With a primary place: pans to it, the card adds "or similar". With none: card shows the activity, mini-map shows the user's area, no pin | Card shows the activity, no pin |
| Go | Directions to the primary place | Directions to the primary place if one exists, otherwise hidden | Hidden |
| Map tab | Yes | Only if it has a primary place | No |
| Reminders (M8) | Eligible | Not eligible in MVP | Not eligible |
| "Needs a place" | Yes, if no place resolved or confidence is low (ledger) | Never (a missing place is by design) | Never |

**Local vs. travel tagging (for the wedge decision):** the main app already asks for When In Use location on first launch (ledger). On each app open it records a coarse location cell (rounded to ~1 km, the ledger's existing coarse-location rule) server-side. The **home area** is a stable value kept separate from current location: the cell present on the most **distinct days** in the last 30 days, with ties going to the cell seen most recently. Counting days rather than opens means heavy app use during a trip can't outweigh home: a 5-day trip moves the home area only if it outnumbers the home days in the window. It counts as established only after opens on at least 3 distinct days. **Storage and retention:** at most one row per user, per day, per cell (`user_id, day, cell`). Rows older than 30 days are deleted by a daily `pg_cron` job and deleted with the account. The privacy policy and consent state exactly this: "coarse (~1 km) area, at most one entry per area per day, kept 30 days, used for the weekly digest and local/travel tagging." Until it's established, tags are `unknown`. Tags are computed against the home area at identification time and aren't recomputed later. At identification, an Experience is tagged `local` if its primary place is within 50 km of the home area, `travel` if farther, and `unknown` if there's no place or no home area (including when location is denied). The privacy policy and consent screen extend the stated purpose of coarse location from "digest" to "digest and local/travel tagging". No new permission prompt.

## Open Questions (founder decisions, flagged, not decided)

1. **No-download rule vs. multimodal eval.** Transcript and video-vision experiments need video/audio. Keep the rule (the experiments stop at caption + thumbnail + web search), or allow a narrow exception (e.g. ephemeral server-side processing, nothing stored)? This is legal and terms exposure, so it's the founder's call. Default until decided: keep the rule.
2. **Tester-visible intent text.** Does a feed card show the inferred activity ("Drive a race car on a real circuit") as its headline, or the place name? It's always labelled estimated per the provenance rule. This goes to the D4 design pass.
3. **Showing alternative interpretations.** When there are several candidates (hotel vs. "see the Northern Lights"), does the one-question sheet offer the interpretations or only places? D4 design pass.
4. **Wedge call after friends' data.** Travel or local. Decided from logged categories, not now.
5. Unchanged: the expansion-gate threshold, the minimum iOS version, the final name.

## What I noticed about how you think

- You wrote "Simply renaming Rhyme's 'spots' to 'experiences' does not create a different product." Most founders who discover a strong competitor reach for a vocabulary difference. You ruled that out before anyone suggested it.
- When asked whether Rhyme failed you, you picked "Yes, and it mostly worked." That's the less comfortable answer, and it's the one that keeps the docs honest.
- "Its existence should raise the quality bar for Experience. It should not prevent Experience from being built." That treats a competitor as a reference point rather than a verdict, which is the useful stance as long as the gap hunt actually happens.
- You chose the company outcome to break ties while naming engineering quality as a fallback. That keeps the gates and metrics in charge of scope.

### R3-1 — consistency (blocking)

**Problem**

> The home area is the mode of app opens, but the document then claims 'A trip therefore doesn't move it.' That claim doesn't follow from the mechanism. People use a saves/map app heavily while traveling, so a 5-day trip with ~10 opens/day outweighs 25 home days at ~1 open/day, and the trip cell becomes the home area. Saves identified during and after that trip are then tagged against the trip location, which reintroduces the R2-1 bias in the data the wedge decision relies on.

**Remedy**

> Count distinct days per cell, not opens (the home area is the cell present on the most distinct days in the last 30 days, optionally weighted toward overnight or first-open-of-day cells), and qualify the claim, e.g. 'a trip shorter than about half the window doesn't move it'.

### R3-2 — completeness (blocking)

**Problem**

> The change replaces 'the latest within 7 days' (one value) with a per-open server-side history of coarse location cells, a location history, but states no retention limit or storage shape. The privacy update extends only the purpose, not what is stored or for how long. A location history with no stated retention is a privacy risk, and testers aren't told about it.

**Remedy**

> State the storage: keep only per-cell distinct-day counts (or per-open rows) for the rolling 30-day window and delete older entries (e.g. via pg_cron), keep it owner-only under RLS, delete it with the account, and have the privacy policy/consent say a 30-day coarse location history is kept to work out the home area.

### R3-3 — completeness (minor)

**Problem**

> Saves identified before the home area is established (the first 3 distinct days, usually a new tester's biggest burst of saves, including any seeded backlog) stay 'unknown' permanently, which removes a large share of the wedge data.

**Remedy**

> Backfill 'unknown' tags once when the home area is first established, while still never recomputing tags that are already set.

**Problem**

**Remedy**
